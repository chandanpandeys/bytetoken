# Reproducible demo results

These are **not production workload claims**. They are the deterministic synthetic developer-like payloads generated by `benchmarks/benchmark_realworld.py` and measured with `o200k_base`.

Source run: GitHub Actions CI run `33813849435`, commit `ede48a6b60707e8b213992b8cb4183bccf8acb6c`, Python 3.11, `tiktoken 0.14.0`.

## Token counts

| Payload | Bytes | Base64 | ByteToken 15-bit | Direct-ID 17-bit* | LZMA + Base64 | LZMA + ByteToken | LZMA + Direct-ID* |
|---|---:|---:|---:|---:|---:|---:|---:|
| JSON API (100 users) | 21,547 | 18,252 | 11,493 | 10,141 | 1,121 | 671 | 593 |
| Pytest-style output | 3,183 | 2,904 | 1,699 | 1,499 | 385 | 223 | 197 |
| CSV analytics (500 rows) | 27,118 | 24,524 | 14,464 | 12,763 | 1,453 | 848 | 749 |
| Python source | 7,906 | 6,386 | 4,218 | 3,722 | 377 | 225 | 199 |
| Build-log text | 11,199 | 9,804 | 5,974 | 5,272 | 792 | 464 | 410 |
| Embedding vector (768 float32) | 3,072 | 2,589 | 1,640 | 1,447 | 278 | 166 | 146 |
| Deterministic random bytes (5 KB) | 5,000 | 4,569 | 2,668 | 2,354 | 4,619 | 2,700 | 2,383 |

`*` Direct-ID numbers are local pre-tokenized-ID representation counts only. They are not hosted-API compatibility claims.

## ByteToken 15-bit savings vs Base64

- JSON API: **37.0% fewer tokens**
- Pytest-style output: **41.5% fewer tokens**
- CSV analytics: **41.0% fewer tokens**
- Python source: **33.9% fewer tokens**
- Build-log text: **39.1% fewer tokens**
- Embedding vector: **36.7% fewer tokens**
- Deterministic random bytes: **41.6% fewer tokens**

These values describe only this tokenizer, implementation, and deterministic benchmark set.

## The compression result that should appear in launch material

The random-byte control is especially useful because it prevents a misleading compression story:

- Base64: 4,569 tokens
- LZMA + Base64: 4,619 tokens (**1.1% worse than Base64**)
- ByteToken 15-bit: 2,668 tokens
- LZMA + ByteToken: 2,700 tokens

That is exactly why the project must keep **compression** and **binary-to-token representation** as separate layers. Compressible JSON/log/CSV payloads gain dramatically from LZMA; high-entropy-ish data does not.

## Three demo cases to lead with

### 1. JSON API payload

Use this when explaining the idea to a broad developer audience.

`21,547 bytes → Base64 18,252 tokens → ByteToken-15 11,493 tokens`

Measured reduction: **37.0%** vs Base64 under `o200k_base`.

### 2. Build logs

Use this for agent/tool-output framing.

`11,199 bytes → Base64 9,804 tokens → ByteToken-15 5,974 tokens`

Measured reduction: **39.1%**.

### 3. Random bytes control

Use this whenever someone asks whether the savings are simply compression.

`5,000 bytes → Base64 4,569 tokens → ByteToken-15 2,668 tokens`

LZMA + Base64 is actually slightly worse than uncompressed Base64 in this control.

## Reproduce

```bash
python -m pip install -e ".[all,dev]"
python benchmarks/benchmark_realworld.py
```

For interactive per-payload measurements:

```bash
python -m pip install -e ".[playground]"
bytetoken playground
```

The Playground additionally performs byte-for-byte encode → decode checks and reports tokenizer-specific counts for `o200k_base` and `cl100k_base`.
