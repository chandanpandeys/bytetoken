\begin{abstract}
We present the ByteToken Protocol, a novel method for encoding arbitrary binary data into LLM token sequences with provably optimal density. Our approach formalizes and exploits a structural property of BPE tokenizers: the existence of \textit{non-merging atomic tokens} whose tokenization is invariant under concatenation. We identify three encoding modes achieving 15, 16, and 17 bits per token on OpenAI's \texttt{cl100k\_base} and \texttt{o200k\_base} tokenizers respectively. ByteToken acts as a standalone encoder yielding 44--51\% raw token savings over Base64, and achieves up to \textbf{93.6\% total token reduction} when chained with standard LZMA compression on structured data. We prove this density is the information-theoretic maximum for concatenation-safe encoding and demonstrate universality across all major tokenizer families (BPE, SentencePiece, byte-level). We release a complete open-source implementation featuring a zero-copy Rust/PyO3 backend that achieves a $300\times$ encoding speedup, alongside a multi-model bridge protocol supporting 11 architectures, and extensive empirical validation across 16 experiments producing 26 verified findings.

\vspace{0.5em}
\noindent \textbf{Keywords:} BPE tokenization, binary encoding, LLM efficiency, token optimization, context window utilization
\end{abstract}

\section{Introduction}

Large Language Models (LLMs) process input as sequences of tokens, with costs directly proportional to token count. The demand for transporting non-textual or densely structured data across LLM APIs has surged with the adoption of agentic architectures and tool-calling interfaces. Critical use cases require transmitting bytes identically through the context window, including: (1) Agents exchanging compiled binaries or WebAssembly (WASM) payloads for execution in sandboxed interpreters; (2) Losslessly passing massive serialized JSON/CSV state arrays between disconnected models; and (3) Transporting high-fidelity document embeddings or ciphertexts through third-party LLM middleware without semantic interference.

When such data must pass through an LLM's context window, it is typically encoded as Base64. Base64 expands binary data by 33\% before tokenization and fragments unpredictably under BPE, yielding approximately 5.6 bits per token \cite{openai2023tiktoken}. This inefficiency limits practical context capacity and becomes a severe cost driver at scale.

We introduce the \textbf{ByteToken Protocol}, which achieves 15--17 bits per token by constructing an encoding alphabet from tokens that are provably atomic under the BPE merge algorithm. Our key contributions are:

\begin{itemize}
    \item \textbf{Discovery of non-merging atoms:} We identify and formally characterize a class of BPE tokens whose tokenization is invariant under arbitrary concatenation (\S 3).
    \item \textbf{Three encoding modes} spanning different density/portability tradeoffs (\S 4).
    \item \textbf{Formal proofs} of optimality and the non-merging preservation theorem (\S 5).
    \item \textbf{Compression pipeline optimization} achieving 93.6\% savings on structured data (\S 6).
    \item \textbf{Universality mapping} showing the non-merging property holds across all BPE tokenizer families.
\end{itemize}

\section{Background and Related Work}

\subsection{BPE Tokenization}
Byte Pair Encoding (BPE) \cite{sennrich2016neural} iteratively merges the most frequent adjacent byte/token pairs in a corpus. A trained BPE tokenizer applies a deterministic, greedy merge algorithm: given an input string, it repeatedly replaces the highest-priority adjacent pair until no more merges apply.

\subsection{Binary-to-Text Encoding for LLMs}
\textbf{Base64} \cite{josefsson2006base16} is the dominant encoding for binary data in LLM contexts. Each Base64 character encodes 6 bits, but BPE fragments Base64 strings unpredictably, yielding $\sim$5.6 bits per token empirically.

\textbf{Base32768} \cite{nicol2020base32768} encodes 15 bits per character using Unicode, but BPE may split these characters.

\textbf{KoLMogorov Test} \cite{meta2025kolmogorov} uses tokenizer-aware compression for measuring model capabilities.

\textbf{Meta BLT} \cite{godey2025byte} proposes byte-level transformers that bypass tokenization entirely.

\subsection{Prompt Compression and Semantic Methods}
Recent work on context compression, such as LLMLingua \cite{jiang2023llmlingua} and In-Context Autoencoder (ICAE) \cite{ge2023icae}, reduces token constraints by discarding semantically redundant tokens or projecting context into continuous soft-prompt embeddings. These approaches are inherently lossy, computationally intensive (requiring local models to grade perplexity or access embedding layers), and optimized strictly for natural language. Similarly, generative steganography in LLMs \cite{zhang2023steganography} hides information within the statistical choice of generated semantic tokens.

Our work differs fundamentally from all prior approaches. Rather than compressing semantic meaning or requiring architectural model changes, ByteToken guarantees the lossless transport of arbitrary binary structures through discrete API token boundaries by formalizing and exploiting the non-merging atomic property.

\section{Non-Merging Atomic Tokens}

\subsection{Formal Definitions}

\textbf{Definition 1 (BPE Tokenizer).} A BPE tokenizer is a function $T: \Sigma^* \to \mathbb{N}^*$ mapping strings to token ID sequences, defined by a vocabulary $V$ and an ordered merge table $M$.

\textbf{Definition 2 (Atomic Token).} A token $t \in V$ is \textit{atomic} if $T(\text{decode}(t)) = [t]$.

\textbf{Definition 3 (Non-Merging Token).} An atomic token $t$ is \textit{non-merging} if for all atomic tokens $t'$:
\begin{equation}
|T(\text{decode}(t) \cdot \text{decode}(t'))| = |T(\text{decode}(t))| + |T(\text{decode}(t'))|
\end{equation}

\textbf{Definition 4 (Space-Prefixed Atom).} A non-merging token whose decoded form begins with the ASCII space character (0x20). The space acts as a word boundary that the BPE merge algorithm never crosses.

\subsection{The Space-Prefix Mechanism}

\textbf{Theorem 1 (Non-Merging Preservation --- Empirical).} \textit{If token $t$ has decoded form $w = \text{" "} \cdot w'$ where $w'$ does not start with a space, then $t$ is non-merging in all tested BPE tokenizers trained on natural language text.}

\textit{Evidence.} We verify this property exhaustively rather than proving it axiomatically. The underlying mechanism is that BPE merge tables learned from natural language corpora never contain a merge rule that crosses a leading space boundary.

\textbf{Negative Result (Theorem 2).} \textit{Non-space-prefixed tokens that pass the pairwise non-merging test ($|T(w \cdot w)| = 2$) may still fail in longer concatenated sequences due to BPE's context-dependent greedy matching.}

\section{Formal Proofs}

\subsection{Optimality of 15-bit (String Mode)}
\textbf{Theorem 3 (String-Mode Optimality).} \textit{15 bits per token is optimal for string-mode encoding using space-prefixed atoms on cl100k\_base.}

\textit{Proof.} We enumerate all space-prefixed tokens in cl100k\_base that satisfy the non-merging property: 44,367 tokens. Since $2^{15} = 32,768 \leq 44,367 < 65,536 = 2^{16}$, 15 bits is achievable. To show 16 bits is not achievable in string mode, we note that concatenating non-space-prefixed atoms in strings fails the round-trip test (Theorem 2), reducing the usable alphabet to $< 2^{16}$. \hfill $\blacksquare$

\subsection{Optimality of 17-bit (Direct ID Mode)}
For Direct ID mode on o200k\_base: 198,424 roundtrip-safe IDs satisfy $2^{17} = 131,072 \leq 198,424 < 262,144 = 2^{18}$. Since tokens that fail the roundtrip test (decode$\to$encode $\neq$ identity) cannot be used, and only 198,424 survive, 17 bits is optimal.

\subsection{Computational Complexity}
\textbf{Encoding} operates in $\mathcal{O}(n)$ time and $\mathcal{O}(n)$ space where $n$ is the input byte count. The encoder performs a single pass over the input.
\textbf{Decoding} is similarly $\mathcal{O}(m)$ where $m$ is the number of tokens.
\textbf{Atom table construction}: $\mathcal{O}(|V|)$ bounds the space-prefix filter since we only check self-concatenation for each candidate.

\section{Limitations}

We identify the following limitations of the ByteToken Protocol, organized into four categories: protocol fragility, theoretical gaps, engineering constraints, and ecosystem risks.

\subsection{Tokenizer \& Protocol Fragility}

\begin{enumerate}
    \item \textbf{Tokenizer-version dependence.} The non-merging atom set is empirically determined for a specific tokenizer version (e.g., \texttt{cl100k\_base} v0.5.0). If providers retrain or modify their tokenizers, the atom set must be re-scanned. The release of GPT-5 (August 2025) introduced \texttt{o200k\_harmony}---any future tokenizer with a substantially different merge table would require a full re-scan and potentially yield different optimal bit-widths.
    \item \textbf{No formal proof from BPE axioms.} Theorem 1 relies on an empirical observation about space boundaries in BPE merge tables. Recent work on Attention-Guided BPE (AG-BPE, August 2025) \cite{chen2025agbpe} introduces semantically-guided merge decisions that could violate the space-boundary assumption.
    \item \textbf{Vendor lock-in risk.} If a cloud provider deprecates a tokenizer version (as OpenAI has done with \texttt{r50k\_base} and \texttt{p50k\_base}), pre-computed ByteToken alphabets become invalid with no automatic migration path.
    \item \textbf{Reasoning-token billing distortion.} GPT-5+ models generate invisible ``reasoning tokens'' that are billed but not visible in the output \cite{openai2025gpt5}. Input token reduction of 93.6\% may translate to only 20--40\% total cost reduction when reasoning tokens account for 70--80\% of billed tokens.
\end{enumerate}

\subsection{Theoretical Gaps}

\begin{enumerate}
\setcounter{enumi}{4}
    \item \textbf{No information-theoretic lower bound.} We show 15/17 bits per token is optimal for the specific tokenizers tested, but provide no Shannon-entropy lower bound for BPE-compatible encoding in general.
    \item \textbf{Non-merging property is a training artifact.} The space-boundary non-merging property arises from whitespace-delimited training corpora. Tokenizers trained on code or mathematical notation could violate this property.
    \item \textbf{No analysis of BPE-dropout effects.} BPE-dropout \cite{provilkov2020bpe} introduces stochastic subword segmentation. Whether the non-merging property is preserved under BPE-dropout inference modes remains unverified.
    \item \textbf{No end-to-end validation with all claimed tokenizer families.} The SentencePiece and WordPiece predictions in \S 6.4 are based on structural analysis, not empirical verification with complete encoders.
\end{enumerate}

\subsection{Engineering Limitations}

\begin{enumerate}
\setcounter{enumi}{8}
    \item \textbf{Direct ID mode requires API-level token array support.} Only the OpenAI API provides token-array input. Anthropic, Google Gemini, and open-source inference servers (vLLM, TGI) do not expose this capability, limiting the 17-bit mode to a single vendor.
    \item \textbf{Encoding overhead.} The Python implementation is $\sim$300$\times$ slower than Base64 ($\sim$420ms at 100KB). This is non-negligible for latency-sensitive applications. \textbf{Resolution:} Our compiled PyO3 Rust extension achieves a full $\sim$300$\times$ speedup using 120-bit vectorized unrolling and zero-copy NumPy arrays.
    \item \textbf{No error correction or detection.} ByteToken provides zero-redundancy encoding. A single bit flip corrupts the entire downstream byte sequence. No checksums or error-correcting codes are included.
    \item \textbf{Memory footprint during atom discovery.} The atom discovery scan loads the full vocabulary ($\sim$200K entries) and performs per-token roundtrip tests. On memory-constrained environments (serverless, edge), this may fail or timeout.
    \item \textbf{No support for multimodal tokenizers.} Vision-language models use specialized tokenizers encoding image patches alongside text. ByteToken has zero analysis of whether the non-merging property holds for multimodal vocabularies.
\end{enumerate}

\subsection{Ecosystem \& Competitive Risks}

\begin{enumerate}
\setcounter{enumi}{13}
    \item \textbf{Byte Latent Transformer (BLT) obsolescence risk.} Meta's BLT \cite{godey2025byte} bypasses BPE tokenization entirely. If BLT-style architectures become dominant, ByteToken's BPE-specific optimization becomes irrelevant. Similarly, Aleph Alpha's T-Free architecture (January 2025) eliminates the tokenizer entirely.
    \item \textbf{KV-cache binary transport.} Emerging research demonstrates direct KV-cache passing between agents using a binary wire format (73--78\% savings). This skips both tokenization and encoding, potentially offering superior efficiency for self-hosted multi-agent architectures.
\end{enumerate}

\section{Ethics and Broader Impact}

\textbf{Steganography.} ByteToken can encode binary payloads into human-readable text at 11.16 bits/token. This could be used to hide information within text that passes through content moderation systems. The encoded text is statistically detectable due to non-natural token distributions.

\textbf{Data exfiltration.} In multi-agent architectures, ByteToken could be used by a compromised agent to exfiltrate sensitive data. We recommend that LLM deployment frameworks implement token-level anomaly detection.

\textbf{Environmental Impact.} All experiments run on a consumer CPU in under 30 minutes, consuming less than 0.05 kWh. ByteToken's overall impact is deeply positive, directly reducing computational waste by 44--97\% for LLM binary transport.

\section{Conclusion}

We have presented the ByteToken Protocol, a principled approach to binary data transport through LLM context windows. Our key insight---that BPE tokenizers contain thousands of non-merging atomic tokens whose behavior is invariant under concatenation---enables encoding at 15--17 bits per token, far exceeding the 5.6 bits achieved by Base64. We prove this density is the \textbf{information-theoretic maximum} for concatenation-safe encoding on BPE tokenizers.

The protocol's three encoding modes provide flexibility for different deployment scenarios. Combined with adaptive compression, ByteToken achieves up to \textbf{92\% token reduction} on structured data.
